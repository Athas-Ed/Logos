### 4.2 讨论说明（FAQ）

**Q1 — Pipeline 与 MCP 包**

- **`pipeline` 是 PR 四范式之一**（与 `dialogue` / `react` / `plan` 并列），由 manifest 的 `paradigm: pipeline` 选中，Shell 走 **`run_pipeline`**，**不会**走 ReAct 循环。  
- 早期 **`设定导入Skill开发.md`** 曾写「Skill（MCP）在 `skills/<包名>/server.py`」——那是 **A6 封存稿的一种实现草图**（把「导入」做成 MCP 工具提供方），**不是**开源第三方包，也**不是**「又一个 Agent 范式」。  
- **定案（与 `Skill形态与Prompt工程.md` §2 一致）**：**产品 Skill** `import_setting` = manifest + **进程内**流水线；**MCP** 仍只承载 **工具**（如 `retrieve`），设定导入的校验/渲染/晋升由 **`src/logos/`** 确定性代码完成。

**Q3 — 是否按范式敲定不同 SSE 规范？**

- **要，但是「共享主干 + 范式扩展」**，不是四套完全独立的 API。  
- **共享（所有范式）**：`error`、`done`；需要自然语言正文时用 **`delta`**（dialogue / plan Phase A 等）。  
- **范式扩展（已有/将增）**：  
  - **`react`**：`reasoning_summary` / `reasoning_full`、`tool_trace_*`、`citations_*`（见 API-V0.2 §3.5）。  
  - **`pipeline`（F6）**：**`pipeline_step`**（阶段名、状态、摘要）、**`pipeline_warning`**（含重叠检测 `warnings[]`）；可选仍用 `delta` 承载 LLM 原始 JSON 片段。  
- **文档落点**：在 **`API-V0.2.md`** 增 **§3.x pipeline 事件表** + `test_sse_chat_contract.py`；GUI `sseChat.ts` 按 `skill_id` / 范式解析扩展事件，避免 Task 页误解析 ReAct 事件。

**Q5 — `skill_id` 与执行路径（三种情况）**

| 请求 | 今天行为 | 产品期望 |
|------|----------|----------|
| **`skill_id` 合法**（如 `lint_zh`、`import_setting`） | 读 manifest → 对应范式执行（dialogue / react / plan / pipeline） | 同左 |
| **`skill_id` 非法/未知** | **HTTP 400** JSON，`detail` 说明（**不**开 SSE） | 同左 |
| **省略 `skill_id`**（字段缺省或空） | **不报错**：回退为 **`chat_inspire`** + 服务端 **WARNING** 日志 | **目标态**：**HTTP 400**（强迫先选 Skill） |

因此：**不是**「没传就不执行」——而是「没传却**仍会执行**，只是悄悄当成 `chat_inspire`。这与技能面板「先选 Skill」不一致，也容易让试验台/旧客户端绕过产品路径。

**与 GUI 的关系**：`TaskPage` / `ChatPage` 在 F5 已带 `skill_id`；问题主要出在 **直接调 API**、**Lab 试验台** 或未来漏传的客户端。

**F6 定案（2026-05-21）**：**维持回退**（不 breaking）；目标态 400 **顺延**至未来契约里程碑。产品 GUI / Task / Chat **必须**带 `skill_id`。

**Q5 — `skill_id` 省略改 HTTP 400 是什么意思？**（简称）= 把上表第三行从「回退 inspire」改为「400 拒绝」；**本阶段不实施**。

**Q6 — M-UI 是什么？**

- **M-UI** = **Manual UI**（**负责人手调视觉**的一步），**不是新功能模块**。  
- 背景：F6-04/05 等 **功能步** 允许占位 CSS；**M-UI（F6-06）** 由你在浏览器/Electron 里调间距、字号、窄屏断点、顶栏标签滚动等，对照 **`GUI开发文档.md` §12.8** 检查清单，**避免** Agent 在大功能 PR 里大面积改样式。  
- 范围：**技能面板、Task 页、`/settings`、`/cache`、`chat_inspire` 对话页、顶栏 Tab**（与 §4.1 Q6 默认一致）。

**Q7 — `pipeline_profile` 与「先通用、后具体模板」**

- **机制**：manifest 字段 **`pipeline_profile: <名字>`** 只负责 **指向一套资源**，不把业务写死在 Python：  
  - `resources/entity_template/<profile>/` — `schema.json`、`render_spec.yaml`、`llm_instructions.md`  
  - `resources/pipelines/<profile>.yaml` — 阶段表（LLM → 校验 → 重叠 → 渲染 → 晋升…）  
- **可以**。F6 与「等你设计好再渲染」**不矛盾**，建议拆成两轨：

| 轨 | 谁做 | 内容 |
|----|------|------|
| **平台轨（F6 必做）** | 工程 | `PipelineRunner`、分步 SSE、`pipeline_profile` 加载、阶段接口（校验/渲染/晋升/重叠 **钩子**）、`import_setting` Task UI、晋升接 `DraftPromotionPort` |
| **业务模板轨（你可后置）** | 产品/你 | **具体** JSON Schema、分类枚举、`render_spec` 路径规则、`pipelines` 阶段顺序与文案；换模板 = **只增/改资源 + 改 manifest 一行** |

- **F6 内置样例**：仓库已有 **`default_import_v0`**（角色/地点等 MVP）→ 仅作 **开发/Reference 金样** 与单测，**不**代表最终「千差万别设定」的定稿。  
- **F6 定案（2026-05-21）**：`import_setting` → **`pipeline_profile: default_import_v0`**（沿用仓库金样，竖切片跑通）。  
- **产品定稿后**：新增 `entity_template/your_profile_v1/` + `pipelines/your_profile_v1.yaml`，manifest 改 **`pipeline_profile: your_profile_v1`** — **无需**改 Runner 主干（除非新增阶段**类型**）。  
- **不采用** F6 另建 `generic_import_v0`（已由产品选择 A 路径）。

**结论**：F6 **先做通用导入平台**；「千差万别」的具体渲染与 pipeline 配置 **随你的模板迭代**，不阻塞 F6-01 / G5 / M-UI 并行。

**Q8 — 「导入 LLM」与 `llm_mode`**

- **导入 LLM** = pipeline 里 **「LLM 产出 JSON」那一阶段** 用的模型，没有第二套供应商。  
- **`llm_mode`**：由 **`GET /api/v1/bootstrap`** 下发（`stub` | `remote`），逻辑在 **`api_v1._resolve_llm_mode`**：无 `llm.api_key` 或 `LOGOS_FORCE_STUB_LLM=1` → `stub`（桩回复，e2e 常见）；否则 `remote`（读 **`config/local.yaml`** 的 `llm.api_key`、`llm.base_url`、`llm.model` 等，`AppSettings` / `build_llm_client`）。  
- **F6 定案**：`import_setting` 的 LLM 阶段与 `lint_zh` / `react` **同一 `LLMClient` 实例**。
