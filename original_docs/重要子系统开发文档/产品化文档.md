# Logos — Electron 桌面产品化指导（分步 · 下阶段主战场）

> **地位**：**不替代** **`GUI开发文档.md`**（进程模型、安全、preload、与后端的契约仍以该文为权威）。本文聚焦 **「从开发者可用的 portable 壳」走向「可对外分发的桌面产品」** 时的**依赖关系、推荐分步与验收粒度**，供 **下阶段**（或单列「产品化里程碑」）排期引用。  
> **现行交付**：第三阶段 **P0** 已提供 Windows **portable**、健康门、退出清理等；第四阶段主线为 **A7 / MCP / Obs**（见 **`第四阶段开发计划.md`**），**安装包、签名、自动更新、真壳 E2E、发布 CI** 按本文**分步延后**，避免与主线抢同一合并窗口。

---

## 1. 产品化目标（用户可感知的「完成态」）

| 能力 | 说明 |
|------|------|
| **可安装** | 用户通过安装向导或商店形态获得开始菜单 / 应用目录项（Windows）；macOS 为 `.app` +（可选）DMG。 |
| **可信任** | **代码签名**（至少 Windows Authenticode；macOS Apple 公证若走分发链则几乎必选），减少 SmartScreen / Gatekeeper 摩擦。 |
| **可更新** | **`electron-updater`** 或等价：渠道、差分/全量包、回滚策略；**强依赖**签名与更新服务器约定。 |
| **可运维** | 崩溃与版本信息可诊断；与 **`logs/maint/electron-shell.log`**、Obs 维护轨文档互链。 |

---

## 2. 依赖关系（为何必须分步）

1. **自动更新** 与 **签名** 强相关：未签名包在 Windows/macOS 上更新体验差且易被拦截。  
2. **安装版** 与 **portable** 并存时，须约定 **默认下载物**、卸载行为、是否与「单实例 + 端口独占」冲突。  
3. **真壳 E2E**（CI 内启动 Electron）会拉长流水线、增大缓存；宜在 **安装路径稳定** 后再接，或与夜间任务挂钩。  
4. **托盘 / 关闭主窗是否退出后端** 属于产品策略，会改变进程模型与文档；与 **`GUI开发文档.md`** §2 一并评审后再改代码。

---

## 3. 推荐分步路线（每步可独立合入）

### 步 A — 文档与配置面（低成本）

| 产出 | 验收 |
|------|------|
| README / **`GUI开发文档.md`** 增加「产品化路线图」互链至本文；列明 **当前仅 portable**、安装版与更新为后续项。 | 新贡献者 10 分钟内能读懂「为何暂无自动更新」。 |

### 步 B — Windows 安装包（NSIS 或等价）

| 产出 | 验收 |
|------|------|
| `electron-builder` 增加 **nsis**（或 dir + 自定义安装脚本二选一）；与 portable **并行产物**；文档写清默认下载推荐。 | 干净 Windows 上双击安装后可启动；卸载后无残留监听端口（与第三阶段退出清理策略一致）。 |

### 步 C — 代码签名（Windows 优先）

| 产出 | 验收 |
|------|------|
| 接入 CI 或本地 **`signtool`** 流程；密钥不入库（Secret / 本机）。 | 已签名 exe 在目标系统上 SmartScreen 行为可接受（以团队接受标准为准）。 |

### 步 D — 自动更新（`electron-updater`）

| 产出 | 验收 |
|------|------|
| 更新清单 URL、渠道（beta/stable）、版本号与 `package.json` / tag 对齐；失败回退与日志。 | 从旧版一键升到新版；故意损坏清单时客户端**明确错误态**、不静默失败。 |

### 步 E — 真壳 E2E（可选与步 B～D 解耦）

| 产出 | 验收 |
|------|------|
| Playwright（或 `@electron-forge` 生态）在 CI 或夜间任务中 **启动真实 Electron** 并断言 health/bootstrap。 | 主分支 PR **可选**不阻塞；夜间或 `workflow_dispatch` 绿即可（由团队定夺）。 |

### 步 F — macOS 与公证（按需）

| 产出 | 验收 |
|------|------|
| `darwin` 目标、`hardenedRuntime`、notarize 脚本。 | 在 Apple 硅/Intel 目标机上 Gatekeeper 下可打开（以账号与证书可用为前提）。 |

**顺序建议**：**A → B → C → D** 串行倾向强；**E** 可与 **B** 后并行试点；**F** 独立里程碑。

---

## 4. 开发要点与风险

- **与 portable 并存**：长期保留 portable 有利于开发者与 CI 排障；安装版面向「非克隆仓库的最终用户」。  
- **Python 运行时**：若未来「自带解释器」改变打包体积与更新策略，须在本文或 **`ARCHITECTURE.md`** 启动拓扑中单独修订。  
- **安全**：更新通道即供应链入口；清单 URL **HTTPS**、校验和或签名块须写死策略。  
- **与第四阶段关系**：第四阶段若实现「设置页展示版本号 / 复制调试信息」，应 **只读** 引用本文小节，**不**提前合入 auto-updater 除非本文件步 D 已立项。
