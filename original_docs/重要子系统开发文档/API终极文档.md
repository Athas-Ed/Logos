# API 终极文档（个人使用场景）

> **地位**：在 **`API-V0.2.md`**（字段级契约）之上的**原则、边界与改进备忘**；默认读者为**本人单机使用**（本机或可信局域网），不替代 V0.2 中的路径与 JSON 形状。  
> **更新**：契约变更仍以 V0.2 + 单测为准；本文仅在策略或「值不值得做」变化时修订。

## 1. 文档分工（读哪份）

| 文档 | 回答的问题 |
|------|------------|
| **`API-V0.2.md`** | 「请求/响应长什么样、事件顺序、错误 code」——**实现与 GUI 必须与此一致**。 |
| **本文** | 「个人项目下 API 做到什么算够、还缺什么算『以后再说』、风险是否可接受」——**不逐字段重复** V0.2。 |

### 1.1 API 相关治理算不算 S&G？

在本仓库的既定分层里（见 **`DECISIONS.md`**、**`ARCHITECTURE.md`**）：

- **`harness/sg_layer`（S&G）**：面向 **Agent 工具执行** — 白名单、路径沙箱、输出过滤、**MCP 子进程**等；治理对象是「模型可调用的工具」及其宿主进程。
- **HTTP / SSE `/api/v1`**：面向 **GUI 与后端的对外契约**，由 **`harness/ii_layer`** 实现；契约文、单测与 Git 钩子属于 **I&I 边界 + 仓库工程纪律**，不是运行时对工具调用的沙箱。

**结论**：API 契约治理**不宜**归并到 S&G **代码包**里实现，也不宜在术语上把「HTTP 契约」说成 S&G 子系统，以免和「工具沙箱」混淆。若需要总览，可在架构文中用一张「治理面」表把 **S&G（工具链）** 与 **I&I + 文档 + hook（接口契约）** **并列**列出即可。

## 2. 个人使用标准下的结论

在当前目标（**仅个人使用**）下：

- **主路径**（`health`、`chat` SSE、与 GUI 对齐的解析）配合 **契约单测**，已达到「可持续改代码而不忘约定」的基线，**不必**为 API 单独引入企业级组件（网关、OAuth、多版本并存服务等）。
- **开发者端点**依赖配置门控，适合「本机开发 + 自己控制 `defaults.yaml` / `local.yaml`」模型；**不要**在公网暴露未加反向代理与鉴权的同一进程。

**一句话**：对个人使用而言，API 子系统的**工程完成度已可视为阶段性够用**；余下多为**体验与演进弹性**，见下文第 4 节。

---

## 3. 已接受的风险（个人场景下合理）

以下在非个人或多租户场景下通常要补，**个人使用可明确接受**，避免无限优化：

1. **无终端用户鉴权**：`127.0.0.1` 或等价信任边界由操作系统与防火墙负责。  
2. **URL 仍为 `/api/v1`**：语义演进靠 **文档版本（V0.2 及后续）** 与变更记录，不强行上 `/v2` URL，除非未来真有对外发布需求。  
3. **部分错误走 HTTP 200 + SSE `error` 事件**：流式对话常见做法；非流式客户端若出现再单独约定。  
4. **`bootstrap` 等未实现能力**：已在 V0.2 标明；不阻塞当前个人闭环。

## 4. 仍「值得知道」的改进方向（按优先级）

下列**不是**必须立刻做；按个人精力从**上到下**考虑即可。

### 4.1 维护习惯（成本最低、收益最高）

**适用**：改动 `src/logos/harness/ii_layer/api_v1.py`，或任何导致 **`/api/v1/*` 路径、SSE `event:` 名、`data` JSON 形状** 与客户端约定变化的相关代码。

**同一 PR（或同一逻辑提交）内按顺序自检：**

| 顺序 | 做什么 | 路径或说明 |
|------|--------|------------|
| 1 | 改实现 | `src/logos/harness/ii_layer/api_v1.py`；若牵涉依赖注入再改 `deps.py` 等 |
| 2 | 改权威契约 | `original_docs/重要子系统开发文档/API-V0.2.md`（事件表、请求体、错误 code、开发者端点） |
| 3 | 锁回归 | `tests/test_stream5_api.py`（新事件或语义变化须有新断言或改现有断言） |
| 4 | 对齐全站类型与解析 | 若前端可见：至少 `src/gui/src/api/sseChat.ts`、`src/gui/src/api/developer.ts`，以及 `src/gui/src/types/` 下与 chat / citation 相关的类型 |

**提交说明（或 PR 描述）固定加一行**，便于检索与对照「HTTP/SSE 变更须同步文档与 GUI」的协作要求：

- 对外契约完全不变时写：**`契约：无变更`**
- 有变更时写：**`契约：已更新 API-V0.2（摘要：……）`**（摘要用短语即可，例如「新增 SSE 事件 foo」）

仅修正实现 bug、且 **SSE 事件名与 JSON 字段与顺序** 与 `API-V0.2.md` 仍一致时：第 2 步可不改正文，但建议在第 2 步文件的「修订记录」表补一行**或**仍在提交说明写 **`契约：无变更`**。

仓库已配置 Cursor 规则 **`.cursor/rules/logos-api-contract.mdc`**，编辑 `api_v1` / `API-V0.2` / 相关单测与 GUI API 时会提示本清单。

**Git 钩子 `commit-msg`**：路径列表见 **`scripts/check_api_contract_commit_msg.py`** 内常量（含 `api_v1`、`deps`、`API-V0.2.md`、`test_stream5_api.py`、`sseChat.ts`、`developer.ts`）。若本次暂存命中其中**任一**路径，而提交说明中**没有**以 `契约：`（或 `契约:`）开头的单独一行，则 **`git commit` 被拒绝**（以 `Merge ` / `Revert ` 开头的说明会自动跳过检查）。

```bash
# 在仓库根执行一次（写入本仓库 .git/config）
git config core.hooksPath .githooks
```

实现脚本：**`scripts/check_api_contract_commit_msg.py`**（由 `.githooks/commit-msg` 调用）。

**更严一档（`pre-commit`）**：若暂存区包含 **`api_v1.py`**、**`ii_layer/deps.py`**、**`sseChat.ts`**、**`developer.ts`** 中任一路径的变更，则**必须同时暂存** **`API-V0.2.md`** 与 **`tests/test_stream5_api.py`**（允许与上一提交相比仅为修订记录、注释或断言微调，但二者须出现在本提交的暂存集合中）。由 **`scripts/check_api_contract_staged_bundle.py`**（`.githooks/pre-commit`）执行。

上述两钩与 `commit-msg` 的检查路径列表，与 **`.cursor/rules/logos-api-contract.mdc`** 保持一致。确需跳过：`git commit --no-verify`。

此项不依赖第三阶段计划即可执行。

### 4.2 配置与首屏（与 A3 重叠）

- **`GET /api/v1/bootstrap`**（及 `ui.default_presentation` / `obs.log_profile` 等）在展示规格中已讨论；**个人使用**下可继续「写死在 GUI 或 local 配置」直到第三阶段排期。

### 4.3 机器可读契约（可选）

- 若 GUI 与后端分叉变多，可考虑 **OpenAPI** 或从 Pydantic 模型导出 schema，减少手写 TS 与后端的漂移。  
- **个人使用、单仓库**：维持「V0.2 + 手写类型」仍可接受；此项列为**弹性增强**。

### 4.4 若未来脱离「仅个人」

再按需补：**鉴权、HTTPS 终止、限流、审计日志、正式 URL 版本策略**等；届时应新建独立决策条目，**本文不预写实现**。
