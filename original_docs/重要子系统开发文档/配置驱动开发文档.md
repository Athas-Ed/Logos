## 1. 目标与边界

### 1.1 什么叫「配置驱动」（本仓库口径）

**配置驱动（Configuration-Driven，CD）** 指：在**不修改** `src/logos/agent/` 执行语义、**不修改** `src/logos/harness/sg_layer/` 安全白名单的前提下，通过**仓库浅层**文件即可：

| 能力 | 典型操作 | 典型路径 |
|------|----------|----------|
| **上架新产品 Skill** | 新增 manifest + L2 Prompt | `skills/manifests/*.yaml`、`resources/prompts/skills/*.md` |
| **调整 Prompt / 语气** | 编辑范式头、Skill 片段、持久化档位片段 | `resources/prompts/**` |
| **挂载外部工具** | 声明 MCP + manifest 点名工具名 | `config/local.yaml`、`skills/<包>/server.py` |
| **调整部署与模型** | 路径、LLM、Obs、并发上限 | `config/*.yaml` |
| **P0 类流水线契约** | 换 schema / 渲染规格 / LLM 说明 | `resources/entity_template/<profile>/` |

**不承诺**「任意终端用户零代码发明第五种 Agent 范式」；**新范式种类**仍属**平台版本**能力（见 §4 CD-4）。

### 1.2 「全新能力形态」的三层含义

| 层级 | 含义 | CD 成熟度（第五阶段后目标） |
|------|------|------------------------------|
| **CD-A** | 新 **产品 Skill**，范式 ∈ {dialogue, react, plan, pipeline} | **F5-08 后接近完成** |
| **CD-B** | 新 **工具**（MCP 或内置） | MCP：**配置 + 新 server.py**；内置：仍需 Python 注册 |
| **CD-C** | 新 **范式** 或 **可执行 pipeline 全链** | **顺延**：CD-3 / CD-4 |

对外讲述建议：

> Logos 是 **Agent-native + 配置治理**：作家能力以 manifest 与资源文件上架；核心负责范式引擎、沙箱与 KSFS 落盘闸门。

## 2. 浅层可改 vs 核心固定（现状快照）

### 2.1 浅层（作者 / 运维 / Skill 工程师）

```text
config/                          # defaults.yaml + local.yaml（密钥不入库）
skills/manifests/<skill_id>.yaml # 产品 Skill 政策
skills/<skill_id>/DESIGN.md      # L1 Blueprint（不进运行时）
skills/<包>/server.py            # 工具 Skill（MCP，可选）
resources/prompts/               # L2 运行时 Prompt 片段
resources/entity_template/       # P0 契约（schema、render_spec、llm_instructions）
resources/ksfs/                  # 叙事知识（数据面，非 Prompt）
workspace/                       # 草稿（P1/P0）
```

**加载锚点（代码只读键，不写业务文案）**：

- `logos.harness.skills_registry.get_skill_manifest(skill_id)`
- `logos.agent.cb.load_prompt_fragment(relative_path)` → 根目录 **`resources/prompts/`**
- `logos.harness.config` → 合并 `config/`

### 2.2 核心（平台工程师；不宜给 Skill 作者改）

```text
src/logos/ports/           # 端口抽象
src/logos/agent/           # Shell、PR、CB 引擎、dialogue/react/plan/pipeline 执行器
src/logos/harness/         # HTTP/SSE、S&G 白名单、MCP 发现、组合根
src/logos/persistence/     # KSFS、HSI、Chroma、晋升
src/logos/infrastructure/  # 检索、LLM 适配
src/gui/                   # 产品壳（逐步改为读 bootstrap，见 CD-1）
```

### 2.3 已知「浅层有文件、核心未接线」项（CD-2 消除）

| 资源文件 | 现状 |
|----------|------|
| `resources/prompts/paradigms/react/base.md` | ✅ F6-01：`build_react_system_message` 加载并替换 `{{TOOLS_JSON}}` |
| `resources/prompts/modes/author.md`、`screenwriter.md` | ✅ F6-01：`load_operating_mode_suffix` / `api_v1._operating_mode_suffix` 读文件 |
| `paradigms/plan/` | Phase A 已落地（F5-09 `outline_plan`） |
| `paradigms/pipeline/` | **F6-02**：`PipelineRunner` + `resources/pipelines/`；**F6-03** 接 HTTP/SSE |

## 3. 与 Prompt 三层、四范式的关系

```text
L1 Blueprint (skills/*/DESIGN.md)
        │ 约束作者
        ▼
L2 Runtime (resources/prompts/ + manifest.prompt_runtime_key)
        │ CB 按 paradigm × tier × skill 拼装
        ▼
L3 messages[]（单次请求；Prompt 回显可检视）
```

**范式**决定 **CB 选哪族片段、Shell 选哪类执行器**（见 **`范式路由与PR定案.md`**）。  
**配置驱动不取代范式**；只让「同一范式下的差异」尽量落在 manifest + L2。

**拼装顺序（定案，与 Skill 形态文档一致）**：

```text
paradigms/<paradigm>/base (+ persistence 子路径若适用)
+ skills/<skill_id>.md   # 由 prompt_runtime_key 解析
+ extra_system（operating_mode、前端 system 补充、MCP 工具提示等，来自宿主）
```

## 4. 分阶段路线图（CD-0～CD-4）

> **实施前提**：建议 **先完成第五阶段 F5-06～F5-10**（至少 F5-08），再按下列阶段推进。理由见 **§6**。

| 阶段 | 名称 | 交付摘要 | 验收（自动/手动） |
|------|------|----------|-------------------|
| **CD-0** | 基线（=F5 末） | manifest 注册表、`skill_id` 契约、PR dialogue/react、任务向导、试验台 | F5-10 勾选；pytest + e2e |
| **CD-1** | 产品 Skill 零代码上架 | **`GET /bootstrap` → `skills[]`**；GUI 面板扫描 manifest，删除写死 `catalog.ts` | pytest bootstrap；e2e 面板见新 yaml |
| **CD-2** | Prompt / 模式资源接线 | react 读 `paradigms/react/base.md`；OM 读 `prompts/modes/*.md`；可选 manifest 覆盖键 | 改 md 后行为变；单测 cb |
| **CD-3** | Plan / Pipeline 可执行 | `PlanRunner` Phase A；`PipelineRunner` + **`resources/pipelines/<profile>.yaml`** 解释器；`entity_template` 引用 | plan demo Skill；import profile 单测 |
| **CD-4** | 深度 CD（可选） | 范式 **Runner 注册表**（减少 `api_v1` 分支）；内置 Tool 声明式注册；`input_schema` 驱动 Task 表单 | 新范式插件 entry point；文档 |

### 4.1 CD-1 与 F5-08 的关系

**F5-08 即 CD-1 在第五阶段计划中的落地步**，不必做两遍：

- 交付：`bootstrap.skills` + `SkillPanelPage` 动态渲染 + `retrieve_qa` 样例。  
- 完成后：**新增 Skill = yaml + md**，无需改 GUI 常量表。

### 4.2 CD-3 与设定导入的关系

**设定导入**的产品语义是 **`paradigm: pipeline` + `persistence_tier: p0`**（见 **`范式路由与PR定案.md` §5**）。  
封存规格见 **`设定导入Skill开发.md`**；契约已在 **`resources/entity_template/default_import_v0/`**。

CD-3 目标：

```text
manifest.pipeline_profile: default_import_v0
        │
        ▼
resources/pipelines/default_import_v0.yaml   # 阶段表（示意）
        │
        ▼
PipelineRunner：llm_json | json_schema | render | promote_gate | …
```

**新增一种导入配置**（换 schema/渲染/阶段顺序）→ 改 **profile 目录 + pipeline yaml**，而非复制 HDL 代码。

### 4.3 CD-4「零代码」诚实上限

即使 CD-4，以下仍需要**发版代码**：

- 新的 **SSE 事件类型**（GUI 要展示新块）
- 新的 **内置工具**实现（非 MCP）
- 新的 **范式 ID**（枚举外第五种，且不用插件注册）
- **LLM 供应商协议**变更（非 OpenAI 兼容）

## 5. 配置清单（作者向）

### 5.1 新增 dialogue / react 产品 Skill（CD-A）

| 步骤 | 文件 |
|------|------|
| 1 | `skills/manifests/<skill_id>.yaml`（必填字段见 `skills_registry.py`） |
| 2 | `resources/prompts/skills/<skill_id>.md`（与 `prompt_runtime_key: skills/<skill_id>` 对应） |
| 3 | 可选 `skills/<skill_id>/DESIGN.md` |
| 4 | CD-1 后：**无需**改 `TaskPage` / `ChatPage`；在 manifest 写 **`ui_instructions`**；仅 bootstrap 失败时维护 `catalog.ts` 回退 |

**manifest 最小示例**（P2 dialogue）：

```yaml
skill_id: my_skill
display_name: 我的能力
description: 面板简介一句
ui_instructions: |
  任务页/对话页「技能说明」正文（可多行）。
persistence_tier: p2
paradigm: dialogue
turn_policy: single
allowed_tools: []
prompt_runtime_key: skills/my_skill
input_schema:
  type: object
  properties:
    text: { type: string, title: 待处理文本 }
  required: [text]
```

### 5.2 挂载 MCP 工具（CD-B）

| 步骤 | 文件 |
|------|------|
| 1 | `skills/<包>/server.py`（FastMCP 工具定义） |
| 2 | `config/local.yaml` → `skills.mcp_servers[]`（`id`、`entrypoint`、`env`） |
| 3 | manifest `allowed_tools: [工具名]` 且 `paradigm: react`（或 dialogue 带工具说明的特殊路径） |

详见 **`MCP开发.md`**。

### 5.3 调整 Prompt 而不改 Python（CD-2 之后）

| 改什么 | 路径 |
|--------|------|
| dialogue 通用头 | `resources/prompts/paradigms/dialogue/base.md` |
| P0/P1/P2 附加约束 | `resources/prompts/paradigms/dialogue/persistence/p{0,1,2}.md`（p0/p1 可补文件） |
| 某 Skill 专有要求 | `resources/prompts/skills/<skill_id>.md` |
| react 通用 JSON 协议 | `resources/prompts/paradigms/react/base.md`（CD-2 接线后） |

### 5.4 部署与运行时（始终）

| 改什么 | 路径 |
|--------|------|
| API Key、代理、模型 | `config/local.yaml` → `llm.*` |
| MCP 开关 | `config/local.yaml` → `skills.mcp_servers` |
| 路径、日志、SSE 并发 | `config/defaults.yaml` / `local.yaml` → `paths.*`、`ui.*`、`obs.*` |
| Prompt 回显（开发） | `config/local.yaml` → `developer.show_dev_tools_ui`、`prompt_echo` |

## 6. 与第五阶段（F5）的先后顺序

### 6.1 建议：**先完成 F5，再做 CD-2～CD-4**

| 顺序 | 理由 |
|------|------|
| **先 F5-06～F5-10** | 任务 JSON v2、`chat_inspire`、**F5-08 bootstrap.skills**、总验收，把**产品主轴**和 **PR 轨**钉死；避免 CD 重构时产品面未稳定。 |
| **后 CD-2** | 把硬编码 Prompt **迁到 resources**，属于**重构**，不改变对外产品故事；与 F5 功能正交。 |
| **后 CD-3** | pipeline/plan **本来就在 F5 标为顺延**；与 F5-08 **无文件冲突**。 |

**结论：可以先做第五阶段，再做配置驱动深化；不仅不冲突，而且 F5-08 已是 CD 的第一块。**

### 6.2  touch 矩阵：哪些文件 F5 会动、CD 会动

| 区域 | F5（剩余）主要改动 | CD（后续）主要改动 | 重叠风险 |
|------|-------------------|-------------------|----------|
| `skills/manifests/` | F5-07 增 `chat_inspire`；F5-08 增 `retrieve_qa` | 持续新增 yaml | **低**：只增文件 |
| `resources/prompts/skills/` | F5-07 文案 | 作者迭代 | **低** |
| `api_v1.py` / `API-V0.2.md` | F5-08 bootstrap；F5-06 若涉 IPC 另议 | CD-3 可能增 pipeline 事件 | **中**：CD-3 时集中改契约 |
| `src/gui/skills/catalog.ts` | F5-08 **删除/替换**为 bootstrap | CD-1 完成后**不再改** | **一次性**：F5-08 即收口 |
| `cb.py` | F5-03 已接 dialogue | CD-2 改 react/OM 加载 | **中**：CD-2 **专门 PR**，避免与 F5-07 同 PR 大改 cb |
| `agent/shell.py`、pipeline | F5-09 可选 Plan A | CD-3 实现 pipeline | **低**：F5-09 可标顺延 |
| `resources/entity_template/` | 一般不动 | CD-3 引用 | **低** |

### 6.3 减少「同一处改两遍」的三条纪律

1. **F5-08 做完即冻结 GUI 写死 Skill 列表**——CD-1 不再重复造 `catalog.ts`。  
2. **CD-2（react/modes 接线）单独开分支/里程碑**——不与 F5-07 功能混合，避免 `cb.py`/`api_v1.py` 同文件拉扯。  
3. **pipeline 全链只在 CD-3 立项**——第五阶段红线已写「不做设定导入 pipeline 全链」，勿在 F5 半途开工 `run_pipeline` 大段逻辑。

### 6.4 若必须坚持「先 CD 再 F5」

仅当产品未上线、可接受 **F5-04/05 面板仍写死 Skill** 时可行；会**延迟** F5-08 的收益。  
**不推荐**：当前 F5-01～05 已交付，回头只做 CD-1 而不做 F5-08 会造成「manifest 已有、面板仍写死」的更长尴尬期。

## 7. 范式 Runner 插件化（CD-4 设计草图）

第五阶段 PR 轨为 **if paradigm 分支**（见 `api_v1.py`、`shell.iter_paradigm_task`）。CD-4 可选演进：

```text
manifest.paradigm
        │
        ▼
PARADIGM_RUNNERS[paradigm].run(skill_id, task_input, …)  →  AsyncIterator[SSE items]
```

- **新增范式**（极少数）：实现 `ParadigmRunner` 协议 + 注册（或 `pyproject.toml` entry points）。  
- **新增 pipeline 变体**（常见）：只增 **`resources/pipelines/*.yaml`**，不增范式枚举。
