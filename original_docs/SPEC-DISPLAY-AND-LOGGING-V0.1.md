# Logos 补充规格 — 展示模式（WM）与日志粒度（V0.1+）

> **文档地位**：在 [`SPEC-V0.1.md`](./SPEC-V0.1.md) 的 V0.1 范围之上，约定 **用户可见内容的展示策略** 与 **日志落盘粒度** 的产品与配置契约。实现 I&I / GUI / Obs 时以本文件为据；若与主 SPEC 的模块清单冲突，以主 SPEC 为准，本文件仅细化「展示与日志」横切需求。
>
> **状态**：已讨论定稿（动工前设计）；**尚未**要求代码与配置键必须已实现，但新增配置与 API 时应与本文件对齐或显式修订本文件。

---

## 1. 术语

| 名称 | 含义 |
|------|------|
| **OM（Operating Mode）** | 业务运行模式：作家（author）/ 编剧（screenwriter）等；控制角色、Prompt、工具策略等，**不**表示「是否展示推理」。 |
| **WM（Work Mode，工作展示模式）** | 面向日常工作的 **用户可见** 展示档位：推理 **摘要**、**部分**引用、工具调用链 **摘要**。 |
| **开发者展示模式（Developer presentation）** | 面向排障与深度可解释性的 **用户可见** 档位：AI 推理 **全过程**（含可能敏感的中间文）、检索 **结构化** 全量或近全量片段、工具调用链 **全过程**。 |
| **日志粒度 / 日志配置** | 仅由 **config**（及环境变量覆盖）控制，决定 Obs **落盘（及等价后端导出）** 记多细；**无** GUI 开关。 |
| **本次浏览器会话** | 自用户打开当前浏览器标签/窗口至关闭（或刷新策略由实现约定）期间有效；**不**写回服务器 config 文件。 |

---

## 2. 设计原则

1. **展示与日志分离**：用户屏幕上显示什么 **不** 决定日志里记什么；两条管道分别由 **展示策略** 与 **日志配置** 控制。
2. **三者正交**：**OM**、**用户展示档位（WM / 开发者展示）**、**日志粒度** 两两 **不绑定**；允许任意合法组合（例如：编剧 OM + WM 展示 + verbose 日志）。
3. **默认值在 config**：新建会话时，GUI 采用的展示档位默认取自 config；用户仅在本地会话内切换，不改变仓库或服务器上的 YAML。
4. **摘要服务端生成**：WM 下展示的推理摘要、引用节选、工具链摘要均由 **服务端** 生成或裁剪，前端只做渲染与折叠，避免依赖完整载荷在前端「自己摘要」导致的一致性与泄密风险。
5. **敏感内容知情**：开发者展示模式可能包含 **敏感或不宜外发** 的中间推理与工具细节；产品需在 UI 或文档中提示，且默认对外部署建议使用 WM + 较粗日志粒度（见 §6）。

## 3. 归属边界（与 Obs / I&I）

| 能力 | 归属 |
|------|------|
| 日志是否记录、字段、级别、保留策略、按粒度过滤 **落盘** | **Obs（配置 + 实现）** |
| 是否向 GUI 下发推理全文/摘要、检索结构化体、工具链全过程 | **I&I（或独立 Presentation 适配层）**：根据 **展示档位**（会话有效值）组装 SSE/API 载荷 |
| 浏览器内档位切换、仅会话有效 | **GUI**（本地状态，如 `sessionStorage` 或等效） |
| OM 切换 | 现有 **config / 请求体** 等既有约定，**不**与展示档位耦合 |

**结论**：「按档位给用户看什么」**不算** Obs 的职责；Obs 负责 **记**。展示策略是 **I&I 与 GUI** 的协作；Obs 只 **消费** 内部事件写日志，规则来自 **日志配置**。

---

## 4. 行为分级（用户可见）

### 4.1 WM（工作展示模式）

- **推理**：仅 **服务端生成的摘要**（非完整 chain-of-thought 原文，除非产品明确将某类安全内容也摘要进固定字段）。
- **引用**：**部分**检索结果（条数、每条条目长度、是否含 score 等由服务端策略固定，可配置）。
- **工具**：工具调用链 **摘要**（例如工具名、状态、耗时、截断后的参数/结果摘要）。

### 4.2 开发者展示模式

- **推理**：**全过程**（含可能含隐私或敏感信息的中间文）；实现上可与模型原始分段对齐，但须遵守主 SPEC 与安全策略中对 **外发** 的约束（若未来有 S&G 审查，审查对象与展示对象仍分离）。
- **检索**：**结构化**展示（例如统一 schema：`path` / `snippet` / `score` / 片段级元数据等），条数与长度上限可仍由 config 限制以防超大响应。
- **工具**：调用链 **全过程**（请求参数、返回体、错误栈等按 config 决定是否再截断；**截断属于展示层策略**，与日志是否全量无关）。

## 5. 配置草案（YAML）

以下键名供实现时采用；合并规则与现有 `defaults.yaml` + `local.yaml` + `LOGOS_*` 一致。

### 5.1 默认展示档位（服务器侧默认值）

```yaml
# 新建浏览器会话时，若 GUI 无本地覆盖，则采用该默认值。
# 枚举建议：work | developer
ui:
  default_presentation: "work"
```

- GUI **仅**在「本次会话」内覆盖该默认值；不写回 `local.yaml`。
- 可选：服务端在只读接口（如 `GET /api/v1/bootstrap`）返回 `default_presentation`，供前端首次渲染；会话内切换 **不** 调用 config 写接口。

### 5.2 日志粒度（仅 config，无 GUI）

```yaml
# 落盘粒度；与 ui.default_presentation、operating_mode 正交。
obs:
  log_profile: "standard"   # 建议枚举：minimal | standard | verbose | audit
```

建议语义（实现可微调，但需在修订本规格时同步更新）：

| `log_profile` | 指向 |
|----------------|------|
| `minimal` | 错误 + 关键里程碑 + 极少上下文 |
| `standard` | 常用排障字段；可对 prompt/正文做长度截断 |
| `verbose` | 更完整上下文；仍可对密钥与 token 做脱敏 |
| `audit` | 合规审计导向的字段集（若有）；与「开发者展示」无绑定 |

**说明**：已有 `config/logging.yaml` 合并入口的，可将 `obs.log_profile` 与现有 logging 段 **并存**，由 Obs 统一解释；或把 `log_profile` 放在 `logging.yaml` 中 **仅** 二选一作为唯一来源——实现时选一种并在本文件后续版本写死。

## 6. 与 API / 流式交互的衔接（与实现对齐，V0.2）

- `POST /api/v1/chat` 以 SSE 为主；**展示档位**由请求体 `presentation`（及 `ui.default_presentation`）决定 **`work`** 与 **`developer`** 两套事件名（与 `DECISIONS.md` / WM·开发者档位一致）。
- **已实现的事件名与载荷**（单行 JSON `data:`）见 **`重要子系统开发文档/API-V0.2.md`** §3.5；摘要如下：

| 语义 | `work`（WM） | `developer` |
|------|----------------|-------------|
| 推理流 | `reasoning_summary` `{text}` | `reasoning_full` `{text}` |
| 引用 | `citations_partial` `{items:[{path,snippet,score}]}` | `citations_full` 同上 |
| 工具轨迹 | `tool_trace_summary` `{tool,status,detail}` | `tool_trace_full` `{tool,arguments,result,error?}` |
| 答复正文 | `delta` | `delta` |
| 结束 / 错误 | `done` / `error` | 同左 |

- **`GET /api/v1/bootstrap`**：返回 `default_presentation`、`log_profile`（`obs.log_profile`）、`operating_mode`，供 GUI 首屏与会话态初始化；**禁止**把「仅开发者可见」的全量对象塞进 WM 默认解析路径。

（具体 JSON 形状与事件名以 `src/logos/harness/ii_layer/api_v1.py`、`tests/test_sse_chat_contract.py` 为权威实现对照。）
