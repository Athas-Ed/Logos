# `已完成/` — 归档区说明

本目录用于存放**已结案、不再作为现行排期或权威依据**的文档原件（例如阶段性计划定稿快照、被新版本完全取代后仍需留档对照的规格片段）。

---

## 何时把文档移入本目录

在以下情况，将对应 Markdown **从 `original_docs/` 根目录或子目录迁入本目录**（或在本目录新建归档副本后，在原文位置改为重定向说明），由提交者在 PR / 提交说明中写清**归档原因**与**现行替代文档**（若有）：

1. **阶段计划执行完毕**：如「下一阶段开发计划」中的某一任务块已验收收口，需保留当时文字作为审计或对照，而主队列不再引用该版本。
2. **契约或规格被新版本取代**：旧版 API、SPEC、决策备忘等已在别处建立新的权威文件（例如 `重要子系统开发文档/API-V0.2.md`），旧文仅作历史对照。
3. **主动冻结**：团队声明某份草案不再更新，仅存档。

**不建议**迁入：仍在迭代的主文档（如 `ARCHITECTURE.md`、`KSFS开发.md`）、当前队列草案（如根目录的 `下一阶段开发计划.md`）。这些应留在原路径并持续更新。

---

## 与 `已完成文档/` 的关系

仓库中另有 **`original_docs/已完成文档/`**（见 `DECISIONS.md` 等处的索引），历史上用于 **V0.1 总 SPEC、DEVPLAN** 等归档批次。

| 目录 | 用途建议 |
|------|-----------|
| **`已完成文档/`** | 与既有「V0.1 归档包」同批、或希望与 `DECISIONS.md` 表格中已有条目并列的长期归档。 |
| **`已完成/`**（本目录） | 其余**已完成计划 / 已退役单文件**的归口；避免与现行 `重要子系统开发文档/` 混放。 |

若某文件更适合与 `已完成文档` 并列管理，可迁入 `已完成文档/` 并在本 README 或 `DECISIONS.md` 中补一行索引，**二选一即可**，勿两处各留一份不同步的副本。

---

## 迁入时的操作习惯

1. **Git**：使用普通 `git mv`（或移动后 `git add`），保留历史 blame 可追溯。
2. **反向链接**：在**现行权威文档**顶部或「修订记录」中增加一行：「旧版见 `已完成/<文件名>`」。
3. **全文检索**：若其他 Markdown 仍链接旧路径，同一提交内尽量批量改为新路径或改为指向现行文档。
4. **命名**：保留原文件名利于对照；若存在多版本，可用后缀或日期区分，例如 `下一阶段开发计划-2026-05-integrate.md`。
